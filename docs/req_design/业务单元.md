# 业务单元

## 1. 功能定位

业务单元模块用于登记企业经营中的基础业务对象，并为后续业务数据提供统一归属维度。

业务单元不是组织架构，也不是单纯数据字典。它是可以被订单、库存、项目、费用、客户、线索、工单等业务数据引用的基础资料。

典型业务单元包括：

- 门店：Mardi 抖音旗舰店、Mardi 京东旗舰店、杭州湖滨店
- 仓库：华东仓、华南仓
- 项目：AI DevOS、直播中台
- 业务线：抖音电商、京东电商
- 投放账号：巨量千川账号、京准通账号

最终目标：

> 业务单元是业务数据的归属维度，也是企业基础业务对象、依赖关系和责任人的统一登记入口。

## 2. 核心口径

页面结构固定为：

```text
类型 -> 分组 -> 列表
```

含义：

- 类型：业务对象的大类，例如门店、仓库、项目、业务线、投放账号。
- 分组：该类型下的统计和筛选分组，例如门店下的抖音、京东、小红书、线下；仓库下的华东、华南。
- 列表：真实登记的业务单元，例如 Mardi 抖音旗舰店、上海仓。

数据字典只有一个：

```text
业务单元
```

字典层级：

```text
业务单元（字典类型）
  门店（一级字典项）
    抖音（二级字典项）
    京东（二级字典项）
    小红书（二级字典项）
    线下（二级字典项）
  仓库（一级字典项）
    华东（二级字典项）
    华南（二级字典项）
  项目（一级字典项）
    内部项目（二级字典项）
    客户项目（二级字典项）
```

数据字典不改表结构，继续使用 `dict_item.parent_id` 表达父子关系。

## 3. 业务单元登记

真实业务单元由用户登记，不是字典项。

新增业务单元字段：

| 字段 | 说明 | 是否必填 |
|---|---|---|
| 业务单元类型 | 来自业务单元字典一级项 | 是 |
| 业务单元分组 | 来自所选类型下的二级项 | 是 |
| 业务单元名称 | 真实对象名称 | 是 |
| 业务单元编码 | 租户内唯一编码 | 是 |
| 父级业务单元 | 用于层级归属和 BI 汇总 | 否 |
| 自定义属性模板 | 用于加载属性键值对模板 | 否 |
| 自定义属性 | 按模板填写后保存为 JSON | 否 |
| 负责组织/负责人 | 使用组织用户选择组件绑定 | 否 |
| 状态 | 启用、停用 | 是 |
| 备注 | 补充说明 | 否 |

示例：

| 类型 | 分组 | 业务单元 |
|---|---|---|
| 门店 | 抖音 | Mardi 抖音旗舰店 |
| 门店 | 京东 | Mardi 京东旗舰店 |
| 仓库 | 华东 | 上海仓 |
| 项目 | 内部项目 | AI DevOS |

## 4. 页面设计

入口：

```text
系统管理 / 业务单元
```

页面分为三块：

| 区域 | 说明 |
|---|---|
| 左侧 | 业务单元类型，展示一级字典项中已有业务单元的类型 |
| 右上 | 当前类型下的分组卡片，展示每个分组下有多少业务单元 |
| 右下 | 当前类型 + 分组下的业务单元列表 |

右上分组卡片示例：

```text
抖音    3 家门店
京东    2 家门店
小红书  1 家门店
```

页面按钮：

```text
新增业务单元
```

不再使用“新增业务资源”作为主入口文案。

## 5. 父子关系

业务单元可以维护父级业务单元，用于层级归属、BI 汇总和数据权限范围。

示例：

```text
华东区
  - 杭州湖滨店
  - 上海旗舰店
```

说明：

- 父子关系表达纵向层级。
- 父子关系不等于业务依赖关系。
- 业务数据可以挂到子业务单元，统计时可向上汇总到父业务单元。

## 6. 关联关系

业务单元之间可以维护横向关联关系，用于表达业务依赖。

示例：

```text
杭州湖滨店 -> 使用 -> 华东仓
Mardi 抖音旗舰店 -> 投放 -> 巨量千川账号
项目 A -> 关联 -> Mardi 抖音旗舰店
```

关联关系要求：

- 支持一个业务单元关联多个业务单元。
- 支持关系类型，例如使用、投放、履约、结算、关联。
- 关系类型可来自数据字典。
- 不能跨租户关联。
- 不能关联已归档业务单元。

## 7. 自定义属性模板

自定义属性用于登记不同类型业务单元的扩展信息。

模板是一组键值对字段定义。新增业务单元时，可以选择加载模板；用户填写值后，前端转换为 JSON 保存。

示例模板：

```text
模板名称：门店基础信息
适用类型：门店
适用分组：空

字段：
- platform_shop_id / 平台店铺 ID / 文本
- shop_level / 店铺等级 / 文本
- open_date / 开店日期 / 日期
- auth_status / 授权状态 / 下拉
```

填写后保存：

```json
{
  "platform_shop_id": "123456",
  "shop_level": "旗舰店",
  "open_date": "2026-05-17",
  "auth_status": "active"
}
```

模板匹配规则：

```text
先匹配：类型 + 分组
再匹配：类型 + 空分组
```

也就是：

- 如果维护了分组专用模板，则该分组加载分组模板。
- 如果没有维护分组专用模板，则加载同类型通用模板。
- 如果两者都没有，则自定义属性为空。

示例：

```text
门店 / 空分组 -> 门店通用信息
门店 / 抖音 -> 抖音门店信息
门店 / 京东 -> 京东门店信息
```

新增时选择：

```text
类型：门店
分组：抖音
```

优先加载：

```text
抖音门店信息
```

## 8. 负责组织和负责人

每个业务单元可以绑定负责组织和负责人，均非必填。

用于后续建立人、组织和业务单元的关系，支撑：

- 根据用户找到负责的业务单元。
- 根据组织找到负责的业务单元。
- 数据权限按业务单元过滤。
- BI 按负责人或负责组织统计。
- 审批或任务流按业务单元负责人流转。

前端复用现有组织用户选择组件：

```text
frontend/src/components/OrgUserPicker.vue
```

组件 key 规则：

```text
c_1  = 公司节点
d_2  = 部门节点
u_10 = 用户
```

保存时转换：

- `c_`、`d_`：负责组织。
- `u_`：负责人。

## 9. 后续业务数据使用方式

后续业务表只需要增加业务单元归属字段：

```text
business_unit_id
```

示例：

```text
orders.business_unit_id
inventory_records.business_unit_id
project_tasks.business_unit_id
expense_records.business_unit_id
customer_records.business_unit_id
```

基于业务单元可以实现：

- 查询某个门店的数据。
- 查询某个平台分组下的所有门店数据。
- 查询某个区域父级下所有子业务单元数据。
- 查询某个负责人负责的业务数据。
- 按业务单元做数据权限和 BI 汇总。

## 10. 验收标准

- 数据字典表结构不变。
- 只使用一个业务单元字典类型。
- 一级字典项作为类型，二级字典项作为分组。
- 页面结构为类型、分组、列表。
- 右上分组卡片能直观看出每个分组下有多少业务单元。
- 新增入口为“新增业务单元”。
- 自定义属性模板支持类型通用和分组专用，分组专用优先。
- 负责组织和负责人非必填，复用 `OrgUserPicker`。
- 父子关系、关联关系、属性 JSON、负责人关系均受租户隔离约束。
