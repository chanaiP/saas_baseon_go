# 当前实现总览

本文档用于帮助新接手的开发者快速理解当前 SaaS 底座的实现边界、运行拓扑、核心链路和验收入口。更细的模块需求、数据库设计、技术方案和测试用例分别放在 `req_design`、`sql_design`、`tech_design`、`test_cases` 目录中。

## 项目定位

当前项目是企业级 SaaS 多租户管理后台底座，目标不是单一业务系统，而是给后续业务模块提供统一的主体、身份、权限、菜单、套餐、配额、审计、字典、参数、组织和文件能力。

当前工程已形成以下基础能力：

- 多主体与平台主体管理。
- C 端个人空间、Account/UserIdentity/AppUser 分离、平台/企业/个人空间类型。
- 套餐、功能点、配额项、订阅与租户覆盖。
- 菜单、操作、权限码、角色授权与租户菜单覆盖。
- 组织架构、岗位、业务单元、用户管理。
- 数据字典、系统参数、登录日志、操作日志。
- 文件上传下载、安全校验与租户归属约束。
- PostgreSQL 迁移、Redis 会话、开发环境 Docker 编排。

## 运行拓扑

本地开发推荐使用以下端口：

- 前端开发服务：`http://127.0.0.1:5174`
- 后端 API 服务：`http://127.0.0.1:8081`
- Docker 前端服务：`http://127.0.0.1:8082`
- PostgreSQL：`127.0.0.1:5432`
- Redis：`127.0.0.1:6379`

默认开发数据库名为 `saas_baseon`，默认开发账号为 `saas/saas`。这些默认值仅允许开发环境使用，生产或准生产环境必须显式配置强密钥、数据库密码、跨域来源和上传目录。

## 后端分层

后端采用 Gin、GORM、PostgreSQL、Redis，代码按以下方向组织：

- `cmd/api`：API 启动入口。
- `cmd/migrate`：数据库迁移入口。
- `internal/bootstrap`：配置、数据库、Redis、路由和种子数据装配。
- `internal/interfaces/http`：路由、middleware、handler、DTO 与统一响应。
- `internal/application`：业务用例服务，承载事务、租户校验、权限校验和审计编排。
- `internal/domain`：领域对象和 repository contract。
- `internal/infrastructure/persistence/postgres`：GORM 模型、repository、schema baseline 与迁移 SQL。

新增后端能力时，优先遵循 `model -> repository -> application service -> dto/handler -> router -> test` 的落位顺序。涉及租户内业务数据时，repository 或 service 必须强制带租户范围，不能依赖前端传入的 `tenant_id` 作为最终可信来源。

## 前端分层

前端使用 Vue 3、TypeScript、Vite、Element Plus。主要目录如下：

- `frontend/src/api`：接口封装。
- `frontend/src/router`：路由定义与守卫。
- `frontend/src/stores`：登录态、菜单、布局等状态。
- `frontend/src/views`：页面。
- `frontend/src/components`：通用组件与业务组件。

前端权限只用于展示和交互体验，后端权限必须兜底。菜单、按钮、快捷入口和租户能力均以后端返回的权限与套餐数据为准。

## 数据库与迁移

当前 schema baseline 位于：

```text
internal/infrastructure/persistence/postgres/schema/current_schema.sql
```

增量迁移位于：

```text
internal/infrastructure/persistence/postgres/migrations/
```

开发环境可以使用自动迁移辅助调试；测试、准生产和生产环境必须通过 `go run ./cmd/migrate` 执行版本化迁移。生产环境禁止依赖 GORM AutoMigrate 修改数据库结构。

## 菜单、权限、套餐链路

项目中最核心的治理链路是：

```text
菜单与操作定义 -> 权限码 -> 套餐功能点 -> 租户订阅与覆盖 -> 租户菜单 -> 角色权限 -> 用户可见菜单与可调用接口
```

这条链路必须保持一致，不能只改页面、只改角色或只改套餐。

执行规则：

- 菜单管理中目录、菜单、操作三层结构是套餐能力矩阵的基础数据来源。
- 只有允许进入套餐中心的功能点才参与套餐开通范围。
- 仅平台能力不得下发给租户侧套餐。
- 仅主体能力只允许租户在自身主体内使用，不进入平台套餐售卖能力。
- 角色权限必须基于当前租户已开通的菜单和操作能力再做授权。
- 后端受保护接口必须有权限码或明确白名单，不能默认放行。

## 主体与租户范围

普通租户用户只能访问当前认证上下文中的主体数据。平台管理员可以进入平台级管理能力，但跨主体能力必须由显式平台权限授予，不能只因为用户属于平台主体就自动获得全局能力。

当前主体已经从单一企业租户扩展为空间容器，通过 `tenant.tenant_type` 区分：

- `platform`：平台治理空间。
- `enterprise`：企业/租户空间。
- `personal`：C 端个人空间。

登录账户、自然人和空间成员已经拆分为 `account`、`user_identity`、`app_user`。业务授权和审计仍以 `app_user + tenant_id` 为准，登录凭证和自然人资料由 `account`、`user_identity` 承载。更多说明见 `docs/tech_design/C端个人空间与账号体系.md`。

涉及主体数据访问时，应遵循：

- 查询、详情、导出、写入、删除都必须带租户范围。
- 前端传入的主体 ID 只能作为业务参数，不能替代认证上下文。
- 逻辑删除、停用、归档必须保留审计线索。
- 用户停用、主体停用、订阅过期、密码变更后，旧会话必须失效或被请求期校验拒绝。

## 套餐与配额

套餐中心负责横向比较不同套餐的能力开通范围和资源限制。功能点负责控制能力是否可用，配额项负责限制数量、容量或调用频率。

配额分为两类：

- 静态配额：不按时间自动重置，例如最大用户数、最大部门数、最大门店数、存储空间。
- 动态配额：按周期统计或重置，例如每日接口调用量、每月导出次数。

配额单位来自数据字典中的平台专属配置，前端只做展示和选择，后端负责最终校验。

## 日志与审计

登录日志记录登录成功、失败、IP、主体、账号和时间。操作日志记录关键写操作的操作者、主体、对象、动作、结果、IP、UA 和 request_id。

新增或修改高风险能力时，必须判断是否需要审计，尤其是：

- 登录、退出、改密、重置密码。
- 主体、套餐、订阅、配额、租户覆盖变更。
- 用户、角色、权限、菜单、组织、岗位变更。
- 文件上传、下载、删除。
- 数据导入、导出。

## 安全基线

项目当前安全基线包括：

- Redis 会话优先，生产环境禁止不可撤销 JWT 兜底。
- 请求期校验用户状态、主体状态、订阅状态和会话有效性。
- 生产环境配置自检，阻断默认密钥、默认数据库密码、危险跨域和自动迁移。
- 文件上传校验扩展名、MIME、magic bytes、大小、路径和压缩包内容。
- 统一错误响应，内部错误写日志，不直接暴露 SQL、Redis、文件系统或堆栈细节。
- 交付包检查，阻断 `.git`、`node_modules`、`dist`、`.DS_Store`、AppleDouble 元数据和临时缓存。

## 文档维护规则

文档必须随代码同步更新。新增业务能力时，应同时检查：

- `req_design` 是否描述业务边界。
- `sql_design` 是否描述表结构、索引、逻辑删除和租户字段。
- `tech_design` 是否描述接口、service、repository、权限、套餐、配额、审计和异常处理。
- `test_cases` 是否覆盖正常流、异常流、权限、租户隔离和回归场景。
- 根目录 `README.md` 是否需要更新启动方式、端口、账号或验收命令。

历史 TODO 和评估报告保留整改过程，不作为当前唯一准入标准。当前开发以 `AGENTS.md`、`CLAUDE.md`、`README.md`、本文档和对应模块设计为准。
