# 应用中心接入强制规则

## 1. 文档定位

本文档约束所有新应用、内置应用和后续业务模块的接入方式。应用中心不是单独页面，而是底座菜单、权限、套餐、租户开通和前后端入口的统一装载入口。

除历史兼容代码外，新增应用必须先完成应用定义，再生成或同步底座能力，不得直接散改菜单、角色权限或套餐功能点。

## 2. app_code 规则

每个应用必须有全局唯一、长期稳定的 `app_code`。

要求：

- `app_code` 一经发布不得随意改名。
- 数据库、后端路由、前端路由、菜单、权限、套餐功能、配额、文档、版本记录必须能通过 `app_code` 串联。
- 系统管理必须作为内置应用登记，建议 `app_code=system-management`。
- 系统监控必须作为内置应用登记，建议 `app_code=system-monitor`。
- 内置应用的 `source` 必须为 `BUILTIN`，不得伪装成普通业务应用。
- 业务系统、业务中台、API 应用、连接器、AI / Agent、组合套件必须各自声明应用类型，不得共用系统管理或系统监控的 `app_code`。

当前内置和规划应用登记口径：

| 应用 | app_code | 类型 | 来源 | 当前状态 | 说明 |
|---|---|---|---|---|---|
| 应用中心 | `app-center` | 系统底座 | 系统内置 | 已上线 | 应用注册、装载规范和平台内置应用治理入口 |
| 系统管理 | `system-management` | 系统底座 | 系统内置 | 已上线 | 用户、角色、菜单、字典、参数等底座治理能力 |
| 系统监控 | `system-monitor` | 系统底座 | 系统内置 | 已上线 | 健康检查、服务器信息、任务、缓存等运维能力 |
| 工作台 | `workbench` | 系统底座 | 系统内置 | 规划中 | 平台与租户用户统一工作入口 |
| 第三方集成中心 | `integration-center` | 连接器 | 系统内置 | 规划中 | 外部系统、开放接口、Webhook 和连接器治理入口 |
| 数据中心 | `data-center` | 业务中台 | 系统内置 | 规划中 | 数据资产、指标、报表和经营看板能力入口 |

应用中心自身也是内置应用，必须通过同样的 `app_code`、菜单、权限和装载记录链路管理，不得作为硬编码例外散落在页面里。

## 3. 工程目录隔离

新增应用必须拥有独立工程目录。底座公共能力可以复用，但应用私有代码不得散落到全局目录中。

后端新增应用默认目录：

```text
internal/apps/{app_slug}/
  app.go
  app.manifest.yaml
  handlers/
  services/
  repositories/
  dto/
  domain/
  tests/
```

前端新增应用默认目录：

```text
frontend/src/apps/{app_code}/
  manifest.ts
  routes.ts
  api.ts
  views/
  components/
  composables/
  types/
```

约束：

- 应用私有 handler、service、repository、view、component、API 调用必须放在应用目录内。
- 跨应用调用只能通过公开 service contract、事件、底座公共服务或稳定 API，不得直接 import 其他应用的私有 service、repository 或组件。
- `internal/bootstrap`、`internal/interfaces/http/middleware`、统一响应、认证、租户、权限、套餐、配额、文件、审计等属于底座公共能力，可以被应用引用。
- 历史模块可以逐步迁移，但新应用不得继续扩大历史散落结构。

## 4. Manifest 装载为唯一入口

应用装载必须以 Manifest 为入口。Manifest 至少声明：

- 应用基础信息：`app_code`、名称、类型、来源、状态、版本。
- 前端入口：路由、菜单入口、客户端类型、是否侧栏显示。
- 后端入口：API 路由、HTTP 方法、权限码、是否公开。
- 权限资源：目录、菜单、操作、API、数据权限资源。
- 套餐资源：可进入套餐中心的功能点、配额项、默认套餐绑定策略。
- 租户可见性：平台专属、租户菜单、仅主体、系统内置。
- 文档与版本：应用文档、发布版本、装载记录。

禁止绕过 Manifest 直接手工写入套餐功能点、租户菜单或角色权限。确需手工维护历史数据时，必须补回 Manifest 或同步脚本，保证下一次装载不会覆盖错误。

## 5. 装载同步链路

应用装载前必须先做规范校验；校验失败时必须拒绝装载，不允许部分写入、静默跳过或降级为手工补录。

应用装载时必须按 `app_code` 同步底座能力：

```text
应用 Manifest
  -> 应用登记
  -> 菜单与权限定义
  -> API 权限矩阵
  -> 套餐中心功能点与配额
  -> 租户菜单与覆盖入口
  -> 角色权限资源
  -> 前端路由与按钮门禁
  -> 后端 service 权限校验
  -> 审计与装载记录
```

同步要求：

- 菜单必须保持目录、菜单、操作三层结构。
- 菜单管理生成的目录、菜单、操作必须按 `app_code` 归属到对应应用。
- 平台专属能力不得进入租户套餐中心。
- 仅主体能力可以进入主体自身能力控制，但不得作为租户可购买套餐能力。
- 租户菜单能力进入套餐中心后，才允许在套餐、租户开通、角色授权链路中出现。
- API 权限必须和操作权限建立对应关系；没有界面操作的内部 API 不得伪装成按钮功能点。
- 角色权限只引用权限资源，不负责决定套餐是否购买。
- 套餐决定租户是否拥有能力，角色权限决定用户是否能操作，数据权限决定用户能看哪些数据。

应用中心菜单要求：

- 顶层目录为“应用中心”。
- 当前已开放菜单为“应用列表”。
- 预留菜单“客户端中心”“租户开通总览”“体验邀请总览”“Manifest 装载记录”“应用审计日志”必须作为应用中心目录下的菜单项登记，未实现前可隐藏或禁用，但不得登记到其他应用。
- “应用分类”当前不作为菜单，不应进入菜单、权限或套餐链路。
- 应用中心是仅平台能力；当前阶段不进入租户套餐中心。

## 6. 幂等与防覆盖

装载必须幂等：

- 同一个 `app_code + resource_code` 重复装载不得生成重复数据。
- Manifest 修改名称、图标、路径、权限码、套餐属性时，应更新对应底座资源。
- 不得覆盖租户自定义菜单名称、图标、启停和排序。
- 不得覆盖租户套餐订阅、租户覆盖值、角色已授权结果。
- 移出套餐中心后，再次装载不得自动加回，除非 Manifest 显式声明恢复进入套餐。
- 平台专属或仅主体归属变更保存时，必须同步从套餐中心移除，并留下装载记录。
- 平台人工维护的“加入套餐中心 / 移出套餐中心”结果必须持久化；服务重启、seed 重跑或 Manifest 重装载不得把已移出的能力重新加入。
- 菜单管理新增、编辑、删除等平台治理操作本身必须进入权限体系，但不得进入套餐中心。

## 7. 数据源统一

菜单、权限、套餐、租户菜单不得各自维护一套互相冲突的数据源。

底座必须保证：

- 菜单管理是目录、菜单、操作的结构来源。
- 应用 Manifest 是应用归属和装载来源。
- 权限表是角色授权和后端校验来源。
- 套餐中心只承载租户可购买能力和配额。
- 租户菜单由套餐、角色权限、租户覆盖共同计算，不单独发明能力。
- 任何从菜单管理生成到套餐中心的能力都必须保留原始父子关系；不得把操作项提升为一级能力，也不得把目录、菜单和操作拆成互不关联的卡片。
- 创建主体时的套餐详情、套餐中心能力矩阵、角色权限配置必须使用同一个树形转换结果。

任何页面如果需要展示功能点，必须使用同一套转换结果，不得在前端临时拼接一份功能列表。

## 8. 准入门禁

新增或调整应用必须满足以下门禁：

- 没有 `app_code` 的应用不得合并。
- 没有 Manifest 的应用不得进入应用中心。
- 没有独立应用目录的新业务应用不得合并。
- 受保护 API 没有权限声明不得启动。
- 平台专属能力进入套餐中心时必须阻断。
- 租户菜单能力没有套餐映射时不得给新租户开通。
- 菜单、权限、套餐之间存在孤儿数据时，检查脚本必须失败。
- 装载重复执行后数据数量必须稳定。
- 新增应用必须补装载同步测试或验收脚本。
- Manifest、目录结构、权限、菜单、套餐、API 或 `app_code` 任一项不符合规范时，应用装载必须失败并返回明确错误，不得生成半成品数据。

## 9. 文档与交接

每个应用必须提供：

- 应用说明。
- Manifest 字段说明。
- 菜单、权限、套餐、配额清单。
- 后端 API 清单。
- 前端路由清单。
- 租户开通与角色授权说明。
- 初始化、装载、卸载、升级和回滚说明。

文档必须使用中文，业务术语必须和页面展示一致。
