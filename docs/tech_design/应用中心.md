# 应用中心

## 1. 定位

应用中心是平台内置应用，用于管理底座内置应用、规划应用和后续装载应用。它不是普通业务页面，而是应用接入、菜单权限、套餐能力和租户开通链路的上游治理入口。

当前阶段只实现平台侧应用列表、应用创建、编辑、详情与启停入口；租户侧应用市场、安装、授权和开通流程不在本阶段范围内。

## 2. 应用标识

应用中心自身按内置应用登记：

| 项 | 值 |
|---|---|
| app_code | `app-center` |
| 应用名称 | 应用中心 |
| 应用类型 | 系统底座 |
| 来源 | 系统内置 |
| 可见范围 | 仅平台 |
| 后端目录 | `internal/apps/app_center` |
| 前端目录 | `frontend/src/apps/app-center` |
| Manifest | `internal/apps/app_center/app.manifest.yaml` |

系统管理、系统监控也必须作为独立内置应用登记，分别使用 `system-management`、`system-monitor`。

## 3. 页面范围

应用中心目录下当前菜单：

| 菜单 | 路由 | 当前状态 | 说明 |
|---|---|---|---|
| 应用列表 | `/apps` | 已实现 | 平台应用列表、筛选、统计、创建、编辑、详情、启停 |
| 客户端中心 | `/apps/clients` | 占位 | 当前显示生产统计占位，后续管理客户端、端能力和发布目标 |
| 租户开通总览 | `/apps/tenant-openings` | 占位 | 当前显示生产统计占位，后续展示租户订阅与应用开通状态 |
| 体验邀请总览 | `/apps/trial-invites` | 占位 | 当前显示生产统计占位，后续管理体验邀请与试用开通 |
| Manifest 装载记录 | `/apps/manifests` | 占位 | 当前显示生产统计占位，后续展示应用装载、升级、失败与回滚记录 |
| 应用审计日志 | `/apps/audit-logs` | 占位 | 当前显示生产统计占位，后续展示应用治理操作审计 |

“应用分类”当前不作为菜单，不进入菜单、权限、套餐链路。应用类型来自应用字段和数据字典，不单独做页面菜单。

### 3.1 当前前端实现状态

应用列表保持现有分组卡片展示，不承载应用资产明细。当前已完成：

- 顶部定位文案为“统一注册、装载、订阅、安装、授权、计费和运行治理；版本、进度与文档由项目管理应用同步。”
- 新增应用弹窗使用大弹窗、左侧锚点、右侧连续滚动表单。
- 新增应用左侧锚点根据基础信息、开通配置、客户端草稿、资产草稿自动打勾。
- Manifest 格式文件由后端 `/api/apps/manifest/template` 输出标准 YAML 模板；Manifest 上传由后端 `/api/apps/manifest/parse` 解析校验后回填表单，不再只做浏览器本地解析。
- 后端 `/api/apps/manifest/scan` 已具备扫描仓内 `app.manifest.yaml|yml|json` 的基础能力，扫描结果会标记已存在 `app_code` 并阻断新建导入。
- 编辑应用弹窗与新增应用保持同一交互结构，`app_code`、来源、状态只读展示。
- 应用详情弹窗已扩展为应用概览、应用主档、可见收费与试用、客户端、入口/API/权限、项目同步信息。
- 启停应用使用后端真实接口，内置应用禁止在应用中心停用或归档。

### 3.2 当前落库边界

当前新增/编辑弹窗中的应用主档扩展信息已随保存写入数据库：

- 部署方式：合并部署 / 独立部署。
- 独立部署通讯方式：平台 API、Webhook、数据同步、网关代理。
- V1 可见范围口径与指定租户草稿。
- 收费策略草稿：先声明免费、收费或非售卖；收费应用再声明订阅制、按量收费或组合收费。组合收费表示订阅制 + 按量收费的组合；价格、周期、计量项和组合规则后续由套餐或计费配置维护。买断不作为独立模型，后续以永久订阅周期表达。
- 试用策略草稿：只声明是否支持试用与试用周期；试用开始统一为租户获得并开通应用时开始。试用期间付费后立即转入付费状态并从付费成功时开始计时；试用期结束仍未付费时终止试用权益。
- 开通方式不再属于应用主档配置。只要租户可见，就可以通过平台统一支持的套餐包含、应用中心订阅开通、邀请码开通获得应用；具体途径记录在租户应用开通记录中。
- 客户端清单。
- 版本、进度、文档入口和版本说明由项目管理应用同步回应用中心，只在详情中只读展示。

入口、API、权限、套餐资源当前仍以 `asset_config` 草稿字段承接，不生成正式权限、API 矩阵或套餐资源。后续若升级为可治理资产，必须新增应用资产表，并同步 Manifest 装载、菜单权限、套餐、租户开通和审计链路。

当前保存到后端 `sys_app` 的字段包括：`app_code`、`app_name`、`icon`、`app_type`、`status`、`charge_mode`、`visibility_scope`、`deployment_mode`、`communication_modes`、`owner`、`version`、`description`、`detail_description`、`sort_order`、`visibility_mode`、`visible_tenants`、`trial_policy`、`trial_start_rule`、`asset_config`、`doc_config`、`release_channel`、`release_note`。客户端清单保存到 `sys_app_client`。历史兼容字段 `open_method` 不再由应用主档维护。

### 3.3 当前概念口径

应用类型回答“应用是什么”，不是前端形态，也不是部署方式。当前字典口径：

| 值 | 名称 | 说明 |
|---|---|---|
| `SYSTEM_APP` | 系统底座 | 账号、权限、菜单、套餐、字典、参数、审计等底座治理能力 |
| `BUSINESS_APP` | 业务系统 | 面向具体业务场景的独立应用，如 CRM、工单、项目管理 |
| `ABILITY_APP` | 业务中台 | 给多个业务系统复用的业务能力中心，如数据中心、消息中心、流程中心 |
| `API_APP` | API 应用 | 主要以 API 对外或对内提供服务的应用 |
| `CONNECTOR_APP` | 连接器 | 负责连接第三方系统、协议、账号或数据源的应用 |
| `AI_APP` | AI / Agent | AI 助手、智能体、模型编排或自动化任务类应用 |
| `SUITE_APP` | 组合套件 | 由多个子应用、能力或连接器组成的产品包，例如“客户经营套件”包含 CRM、营销自动化、客服工单和数据看板 |

客户端是呈现形态，不再作为应用类型。PC Web、API Only、H5、iOS、Android、鸿蒙、桌面端、小程序等都登记在 `sys_app_client`。

部署方式只保留两类：

| 值 | 名称 | 说明 |
|---|---|---|
| `MERGED` | 合并部署 | 应用代码与底座在同一工程或同一运行单元内，通常通过内部路由和同服务 API 使用底座能力 |
| `STANDALONE` | 独立部署 | 前后端或运行服务与底座分离，但仍必须在应用中心登记，受菜单、权限、套餐、租户开通和审计控制 |

独立部署时可登记通讯方式：

| 值 | 名称 | 说明 |
|---|---|---|
| `PLATFORM_API` | 平台 API | 外部应用主动调用底座开放 API |
| `WEBHOOK` | Webhook | 底座或应用在事件发生时向对方推送通知 |
| `DATA_SYNC` | 数据同步 | 双方通过任务、增量同步或消息管道同步数据，仍需受底座授权范围和审计约束 |
| `GATEWAY_PROXY` | 网关代理 | 流量先进入底座或网关，由底座做认证、鉴权、限流、审计后转发到独立应用 |

### 3.4 新建与 Manifest 导入落地方案

应用中心的新建能力分为两条路径：手工新建应用主档，以及通过 Manifest 导入或扫描生成应用主档。两条路径最终进入同一套主档、客户端、菜单、权限、API、套餐和配额同步流程。

#### 3.4.1 页面入口

应用列表右上角保留现有列表内容与筛选区，只新增两个入口：

| 入口 | 位置 | 行为 |
|---|---|---|
| Manifest 格式文件 | 新建应用按钮左侧 | 下载标准 Manifest 示例文件，包含应用主档、客户端、菜单、操作、权限、API、套餐功能点和配额示例 |
| 新建应用 | 操作区主按钮 | 打开新建弹窗，顶部选择“手工填写”或“Manifest 导入” |

新建弹窗不使用“上一步 / 下一步”，右侧为连续滚动表单，左侧为弱化锚点。锚点只做定位和完成状态提示，不作为步骤限制。

弹窗分区：

| 分区 | 手工填写 | Manifest 导入后 |
|---|---|---|
| 基础信息 | 必填，创建应用主档 | 由 Manifest 回填，可修改 |
| 可见范围 | 必填 | 由 Manifest 回填，可修改 |
| 收费策略 | 必填；第一层免费、收费、非售卖；收费再选择收费模式和是否允许试用 | 由 Manifest 回填，可修改 |
| 客户端配置 | 默认不选中，从 `app_client_type` 数据字典读取 | 由 Manifest 回填，可修改 |
| Manifest 解析结果 | 不展示 | 展示 app_code、文件来源、校验状态、资源数量、冲突数量 |

点击“创建应用主档”后必须弹出二次确认。确认文案应说明：当前只创建应用主档与导入草稿，正式菜单、权限、套餐和配额同步需要经过 Manifest 装载确认。

#### 3.4.2 Manifest 来源

Manifest 获取方式按阶段实现：

| 阶段 | 来源 | 说明 |
|---|---|---|
| V1 | 文件上传 | 用户选择 `app.manifest.json` 或 `app.manifest.yaml`，后端解析校验后回填表单，后续保存原始文件摘要 |
| V1 | 合并工程扫描 | 平台扫描当前代码仓库的约定路径，发现合并部署应用 Manifest；当前后端已提供扫描接口 |
| V2 | Git 仓库 | 输入仓库地址、分支和路径，由后端拉取并扫描 |
| V2 | 制品包 | 上传 zip/tar 制品包，后端解包扫描 Manifest |
| V2 | 独立应用回调 | 独立部署应用通过开放 API 上报 Manifest |

合并工程扫描路径：

```text
internal/apps/**/app.manifest.*
frontend/src/apps/**/app.manifest.*
apps/**/app.manifest.*
```

独立部署应用必须通过上传、Git、制品包或回调提供 Manifest。没有 Manifest 的独立应用只能保存为规划主档，不能装载菜单、权限、套餐和配额。

#### 3.4.3 Manifest 标准结构

标准 Manifest 必须至少支持以下结构：

```json
{
  "manifest_version": "1.0",
  "fragment_role": "main",
  "app": {
    "app_code": "crm",
    "app_name": "客户管理",
    "app_type": "BUSINESS_APP",
    "source": "MANIFEST",
    "deployment_mode": "MERGED",
    "communication_modes": [],
    "visibility_scope": "TENANT",
    "charge_policy": "PAID",
    "billing_mode": "SUBSCRIPTION",
    "trial_enabled": true,
    "trial_policy": "TRIAL_15_DAYS",
    "open_api_scopes": [],
    "tenant_context": "",
    "signature_strategy": "",
    "idempotency_strategy": ""
  },
  "clients": ["PC_WEB", "API_ONLY"],
  "menus": [],
  "operations": [],
  "permissions": [],
  "apis": [],
  "package_features": [],
  "quotas": [],
  "documents": []
}
```

字段口径：

| 字段 | 规则 |
|---|---|
| `manifest_version` | Manifest 结构版本，不等于应用业务版本 |
| `fragment_role` | 多文件片段角色，允许 `main`、`frontend`、`backend`、`menu`、`permission`、`api`、`package`、`quota` |
| `app.app_code` | 全局唯一，数据库存在时不能走新建导入 |
| `app.communication_modes` | 独立部署必填，可选 `PLATFORM_API`、`WEBHOOK`、`DATA_SYNC`、`GATEWAY_PROXY`；合并部署留空 |
| `app.open_api_scopes` | 独立部署必填，只声明所需 scope，不发放真实凭证 |
| `app.tenant_context` | 独立部署必填，声明租户上下文来源 |
| `app.signature_strategy` | 独立部署必填，声明请求或事件签名方案 |
| `app.idempotency_strategy` | 独立部署必填，声明 Webhook、同步或写入请求幂等策略 |
| `clients` | 使用 `app_client_type` 数据字典，如 `PC_WEB`、`API_ONLY`、`WECHAT`、`DINGTALK`、`FEISHU` |
| `menus` | 声明目录、菜单、路由、排序、是否租户可见、是否可套餐化 |
| `operations` | 声明按钮或操作项，必须挂到菜单或业务资源 |
| `permissions` | 声明权限码、权限类型、后端校验点和归属 |
| `apis` | 声明 HTTP 方法、路径、权限码、是否公开、审计策略 |
| `package_features` | 声明进入套餐中心的功能点，必须能追溯到菜单、操作或服务能力 |
| `quotas` | 声明配额编码、单位、周期、默认值和是否进入套餐 |

Manifest 装载保护规则：

- 应用资产表保留 `managed_by_manifest`、`manifest_hash`、`last_synced_at`，用于判断资源是否仍由 Manifest 托管。
- 非 Manifest 托管或人工移出托管的资产必须写入 `protection_source`、`protection_reason`、`protected_at`，后续 Manifest diff 识别为冲突，不允许直接覆盖。
- 租户菜单覆盖、套餐功能覆盖、配额覆盖、租户订阅、角色授权均保留 `source` 和 `source_ref`，默认人工操作为 `MANUAL`，系统初始化为 `SYSTEM`，后续应用开通或邀请码链路可写入 `PACKAGE`、`SUBSCRIPTION`、`INVITE` 等来源。
- Manifest 重装载只能更新 Manifest 托管资产，不得覆盖租户覆盖、角色授权、订阅关系或人工保护资源。
- 历史菜单、权限、套餐功能和配额通过一次性初始化迁移写入 Manifest 治理表，`manifest_hash=LEGACY_BASELINE`。该基线只用于识别“库内已有”，避免运行目录扫描反复显示为新增；未被当前 Manifest 声明的历史基线资源不进入“停用” diff，待对应应用 Manifest 明确声明后再转为正式托管。

#### 3.4.4 多 Manifest 与冲突处理

扫描到多份 Manifest 时，后端必须先解析成候选集，再让用户选择导入或同步范围。

处理规则：

| 场景 | 处理 |
|---|---|
| 多份不同 `app_code` | 展示为多个候选应用，可多选导入 |
| 同一 `app_code` 多个片段 | 按 `fragment_role` 合并预览 |
| 同一 `app_code` 多个 `main` | 标记冲突，禁止自动导入 |
| 主档字段冲突 | 标记冲突，用户选择保留哪份或取消 |
| 菜单 path 冲突 | 如果归属同一资源编码则更新，否则阻断 |
| 权限码冲突 | 如果权限归属不同或含义不同则阻断 |
| API method + path 冲突 | 如果权限码不同则阻断 |
| 套餐功能码或配额码冲突 | 如果归属不同或单位不同则阻断 |
| 数据库已存在 `app_code` | 禁止新建导入，只能进入 Manifest 同步 / 升级 |

新建导入只能写入数据库不存在的 `app_code`。如果扫描结果里有 5 个应用，其中 2 个已存在、3 个未存在，页面只能勾选 3 个未存在应用做新建导入；已存在应用显示“已登记，只能同步升级”。

#### 3.4.5 后端接口设计

V1 建议接口：

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/apps/manifest/template` | 下载 Manifest 示例文件 |
| `POST` | `/api/apps/manifest/parse` | 上传 Manifest 文件并解析校验，不写正式资源 |
| `POST` | `/api/apps/manifest/scan` | 扫描合并工程约定路径，返回候选 Manifest |
| `POST` | `/api/apps/manifest/diff` | 将候选 Manifest 与数据库现状比对，返回新增、更新、冲突和阻断项 |
| `POST` | `/api/apps` | 手工创建或基于 Manifest 创建应用主档 |
| `POST` | `/api/apps/manifest/load` | 确认装载 Manifest，写入菜单、权限、API、套餐、配额和客户端 |
| `GET` | `/api/apps/:appCode/manifest/loads` | 查看装载记录 |

接口分层：

```text
handler
  -> manifest parser
  -> manifest validator
  -> manifest diff service
  -> app service
  -> menu / permission / plan / quota sync service
  -> load record repository
```

解析、校验、diff 和装载必须拆开。解析失败不落库；diff 有阻断项不允许装载；装载写入必须在事务中执行，并记录审计日志。

#### 3.4.6 数据模型建议

在现有 `sys_app` 和 `sys_app_client` 基础上，新增正式资源表和装载记录表：

| 表 | 作用 |
|---|---|
| `sys_app_manifest_load` | Manifest 装载批次，记录来源、hash、版本、操作人、结果、错误摘要 |
| `sys_app_manifest_file` | 记录扫描或上传到的 Manifest 文件，包含路径、片段角色、hash、原始内容摘要 |
| `sys_app_entry` | 应用入口与菜单模板 |
| `sys_app_api` | 应用 API 清单与权限绑定 |
| `sys_app_permission` | 应用权限点模板 |
| `sys_app_package_feature` | 应用套餐功能点模板 |
| `sys_app_quota` | 应用配额模板 |

同步到既有底座表时必须保留追溯字段：

- `app_code`。
- `source_manifest_id` 或 `manifest_file_id`。
- `manifest_hash`。
- `manifest_version`。
- `managed_by_manifest`。
- `last_synced_at`。
- `manual_override` 或等价保护标记。

删除策略：

- Manifest 移除资源时，不做物理删除。
- 菜单、权限、API、套餐功能和配额默认进入停用、归档或移出套餐 diff。
- `LEGACY_BASELINE` 历史基线资源只作为初始化对照，不因某个 Manifest 未声明就自动进入停用 diff。
- 已被租户订阅、角色授权、套餐引用或审计引用的资源必须保留历史。

#### 3.4.7 验收口径

V1 完成标准：

- 手工新建能创建应用主档和客户端配置。
- Manifest 文件能下载模板、上传解析、回填表单并创建应用主档。
- 合并工程扫描能列出候选 Manifest。
- 数据库已存在 `app_code` 时，新建导入被阻断并提示只能同步升级。
- 多 Manifest 候选能按 `app_code` 分组展示；同一 `app_code` 冲突时禁止自动导入。
- 客户端配置从 `app_client_type` 数据字典读取，默认不选中，企业微信、钉钉、飞书拆开。
- 收费策略必须先选免费、收费或非售卖；收费后再选收费模式和是否允许试用。
- 未正式装载前，菜单、权限、套餐和配额只作为草稿或 diff 展示，不误写正式运行表。

## 4. 数据模型

当前应用主表为 `sys_app`，核心字段：

| 字段 | 说明 |
|---|---|
| `app_code` | 全局唯一应用编码，发布后不得随意修改 |
| `app_name` | 应用名称 |
| `description` | 一句话介绍，用于应用列表卡片 |
| `detail_description` | 应用详细介绍，可承载富文本内容 |
| `app_type` | 应用类型，如系统底座、业务系统、业务中台、API 应用、连接器、AI / Agent、组合套件 |
| `source` | 应用来源，如系统内置、手工创建、声明文件装载 |
| `status` | 状态，如立项、规划中、开发中、Beta、已上线、已停用；其中建设过程状态由项目管理应用同步 |
| `charge_mode` | 收费策略，如免费、订阅制、按量收费、组合收费、非售卖；组合收费表示订阅制 + 按量收费，不在主档里声明价格、周期、计量项 |
| `visibility_scope` | 可见范围，如仅平台、租户可用 |
| `deployment_mode` | 部署方式，合并部署或独立部署 |
| `communication_modes` | 独立部署通讯方式，多值用逗号保存 |
| `visibility_mode` | V1 可见口径，如全部租户、指定租户 |
| `visible_tenants` | 指定租户或可见说明草稿 |
| `trial_policy` | 试用策略，如不支持试用、7 天、15 天、30 天、不限期 |
| `trial_start_rule` | 试用开始规则，当前统一为获得并开通时开始 |
| `asset_config` | 入口/API/权限/套餐资源草稿，当前不生成正式资源 |
| `doc_config` | 项目管理同步的文档入口或文档摘要 |
| `release_channel` | 项目管理同步的版本渠道 |
| `release_note` | 项目管理同步的版本说明 |
| `is_builtin` | 是否系统内置 |
| `is_platform_only` | 是否仅平台可见 |
| `sort_order` | 排序 |
| `deleted_at` | 逻辑删除字段 |

客户端清单表为 `sys_app_client`，按 `app_id + client_code` 唯一约束，当前用于记录 PC Web、API Only、H5、iOS、Android、鸿蒙、桌面端、小程序和企微/钉钉/飞书等访问形态。

新增或调整字段时必须同步 DTO、前端类型、migration、schema baseline 和本文档。

## 5. 接口与权限

应用中心接口必须是平台侧受保护接口，后端权限兜底，前端按钮隐藏不能替代后端校验。

当前接口语义：

| 能力 | 当前权限资源 | 说明 |
|---|---|---|
| 应用列表 | `/apps` | 查询应用列表与筛选结果 |
| 应用详情 | `/apps` | 查询应用详情 |
| 新增应用 | `app:create` | 新增平台登记应用 |
| 编辑应用 | `app:edit` | 编辑应用基础信息 |
| 启停应用 | `app:status` | 调整非内置应用状态 |
| 装载应用 | `app:load` | 后续 Manifest 装载入口 |
| 查看装载记录 | `/apps/manifests` | 后续装载记录入口 |

权限资源必须挂在 `app-center` 应用下，不能挂到系统管理或系统监控。

## 6. 统计与筛选

顶部统计用于快速筛选应用列表：

| 统计项 | 口径 |
|---|---|
| 所有应用 | 未逻辑删除的全部应用 |
| 已上线 | `status=ONLINE` |
| Beta 版 | `status=BETA` |
| 规划开发中 | `status=PLANNED` 与 `status=DEVELOPING` |
| 已停用 | `status=DISABLED` |

点击统计卡片应同步筛选下方列表；重置按钮只在存在筛选条件时显示。

## 7. 与菜单、套餐、角色的关系

应用中心必须遵守统一链路：

```text
应用登记 / Manifest
  -> 应用菜单
  -> 权限资源
  -> API 权限矩阵
  -> 套餐功能与配额
  -> 租户菜单覆盖
  -> 角色权限
```

当前应用中心为仅平台能力，不进入租户套餐中心。后续业务应用如果需要进入套餐，必须由 Manifest 或菜单管理生成目录、菜单、操作三层树，再同步到套餐中心，不能在套餐中心手工维护另一棵树。

## 8. 初始化与幂等

应用中心 seed 和 migration 必须幂等：

- 重复执行不得生成重复 `sys_app`。
- 不得覆盖人工编辑的应用状态、排序和说明，除非执行显式纠偏脚本。
- 新增规划应用时必须先登记 `app_code`、类型、来源、状态和可见范围。
- 已停用或逻辑删除的应用不得在前端列表中被误判为可用。
- 已存在于旧表的菜单、权限、套餐功能和配额必须初始化进 Manifest 治理表，防止后续扫描更新时把历史资源误判为新增资源。

## 9. 外部调用底座能力待建设

当前底座已具备管理端 HTTP API、登录态、菜单权限包、用户/角色/权限/租户/字典/参数等内部能力，能支撑合并部署应用通过内置路由和同服务 API 使用底座能力。

独立部署应用或外部系统如果要使用底座账户、权限、组织、审计等能力，目前还缺少正式外部接入层，后续需要单独建设：

- SSO/OIDC 或等价身份互认机制。
- 外部应用凭证，如 `client_id`、`client_secret`、服务到服务 token 或 API Key。
- 标准化开放 API，包括用户、组织、租户、权限校验、字典参数、审计上报。
- 外部应用授权范围和 scope 管理。
- 应用中心维护外部应用的回调地址、API 地址、健康检查地址和通讯方式。

这条线不应和应用类型混在一起。应用类型回答应用是什么，部署方式回答是否与底座合并部署，通讯方式回答独立应用如何和底座交换请求或数据，外部调用能力回答独立应用如何安全使用底座公共能力。

## 10. 验收清单

- 应用列表使用真实 `sys_app` 数据。
- 顶部统计与列表筛选口径一致。
- 应用类型分组展示宽度一致，卡片不越界。
- 搜索区和操作区左右分离，搜索条件一行展示。
- 新增、编辑弹窗使用左侧锚点和右侧滚动表单，字段宽度不越界。
- 详情弹窗按应用概览、主档、可见开通、客户端、资产、项目同步信息分区展示。
- 刷新浏览器后，顶栏、左侧菜单、面包屑和当前页面保持一致。
- 应用中心菜单和权限只挂在 `app-center`，不散落到系统管理或系统监控。
