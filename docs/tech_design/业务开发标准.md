# 业务开发标准

## 1. 文档定位

本文档用于规范在 SaaS Baseon 底座上新增业务模块的开发方式。它不是单个功能需求文档，也不是接口文档，而是业务模块接入底座能力时必须遵守的准入标准。

适用对象：

- 后续业务模块开发者
- 测试人员
- 技术负责人
- AI coding agent

强制工程规则仍以根目录 `CLAUDE.md` 为准；本文件只整理业务模块接入时的标准流程和检查项。

## 2. 业务模块准入清单

新增业务模块前，必须先明确以下问题：

| 问题 | 说明 |
|---|---|
| 属于哪个应用 | 必须声明 `app_code`、应用类型、应用来源和 Manifest 路径 |
| 工程目录在哪里 | 新应用必须有独立后端与前端应用目录 |
| 业务对象是什么 | 例如商品、店铺、任务、素材、订单、AI Agent 等 |
| 是否属于租户数据 | 租户内业务数据必须带 `tenant_id` |
| 是否归属组织 | 如公司、部门、门店、仓库等 |
| 是否归属业务单元 | 如区域、项目、门店经营单元等 |
| 是否有状态 | 启用/停用、草稿/发布、成功/失败等 |
| 是否需要逻辑删除 | 业务主数据默认必须逻辑删除 |
| 是否需要菜单入口 | 没有菜单入口也可能需要操作/API/服务能力 |
| 是否需要按钮/操作权限 | 新增、编辑、归档、导入、导出、发布、审核等 |
| 权限归属是什么 | 系统内置、仅平台、租户菜单、仅主体必须明确 |
| 是否由菜单管理生成 | 目录、菜单、操作默认由菜单管理或 Manifest 装载生成 |
| 是否进入套餐 | 是否是租户可购买能力 |
| 是否有配额 | 静态上限或周期消耗 |
| 是否需要数据权限 | 按组织、本人、业务单元、自定义范围等 |
| 是否需要字典/参数 | 类型、状态、策略阈值、默认配置等 |
| 是否需要日志审计 | 写操作、权限变更、导入导出、状态流转等 |
| 是否涉及文件 | 上传、下载、删除、导入、导出 |

没有明确上述问题前，不应直接开始写页面或接口。

## 3. 标准接入链路

新增可操作业务能力必须按以下顺序接入：

```text
应用定义 / Manifest 装载（app_code）
  -> 菜单与权限定义
  -> 套餐功能映射
  -> 租户菜单（含覆盖）
  -> 角色权限
  -> 前端页面与按钮
  -> 后端接口与 service 校验
  -> 数据权限
  -> 审计日志
  -> 测试与文档
```

不得只改前端页面，也不得只给角色授权后绕过套餐、租户菜单或后端二次校验。

应用中心是新增应用的上游入口。新应用必须遵守 `docs/tech_design/应用中心接入强制规则.md`：

- 必须先定义全局唯一 `app_code` 和应用 Manifest。
- 必须拥有独立后端目录 `internal/apps/{app_slug}` 和前端目录 `frontend/src/apps/{app_code}`。
- 应用装载必须同步生成或更新底座菜单、权限、API 权限矩阵、套餐中心功能点/配额、租户菜单入口和角色权限资源。
- Manifest、目录结构、权限、菜单、套餐、API 或 `app_code` 任一项不符合规范时，必须拒绝装载，不允许生成半成品数据。
- `系统管理`、`系统监控` 均按内置应用登记，分别拥有独立 `app_code`。

菜单管理、角色权限、套餐中心和租户开通页必须使用同一套转换结果：

- 菜单管理是目录、菜单、操作三层结构的唯一结构来源。
- 应用 Manifest 是应用归属、默认路由、装载策略和初始能力声明来源。
- 套餐中心只管理租户可购买能力和配额，不得维护另一套重复功能树。
- 菜单管理生成的能力进入套餐时，必须始终以“目录 -> 菜单 -> 操作”三层展示；套餐矩阵、创建主体时的套餐详情、角色权限配置都必须一致。
- “查看”默认属于菜单可访问和数据权限控制，不应作为操作按钮进入套餐，除非页面存在真实独立的“查看”按钮或后端存在必须单独授权的查看动作。
- 应用、菜单、权限、套餐之间出现孤儿数据、重复数据或归属冲突时，应优先修复同步脚本和 seed 幂等逻辑，不得只在前端临时隐藏。

## 4. 后端开发标准

后端新增应用默认按应用目录落位：

```text
internal/apps/{app_slug}/
  app.go
  app.manifest.yaml
  handlers/
  services/
  repositories/
  dto/
  domain/
  tests/
```

历史兼容模块可继续按现有分层维护：

```text
internal/infrastructure/persistence/postgres/models
internal/interfaces/http/dto/{module}.go
internal/infrastructure/persistence/postgres/repositories/{module}.go
internal/application/{module}_service.go
internal/interfaces/http/handlers/{module}.go
internal/application 与 internal/domain 的 *_test.go/test_{module}_service.go
```

要求：

- router 只做 HTTP 边界、依赖注入、权限依赖、响应包装。
- service 负责业务规则、权限/套餐/配额校验、事务编排、审计日志和异常转换。
- repository 只做数据访问，租户内数据必须带 `tenant_id` 过滤。
- 新增业务模块的 repository 默认必须 tenant-scoped；任何 list/detail/update/delete/export/import 查询都必须在 repository 或 service 入参中显式接收租户上下文并补 tenant scope 测试。
- 新增电商业务模块前，必须先提交 tenant scope 回归测试，证明普通租户无法通过 query/body/path 伪造 `tenant_id` 访问其他租户数据。
- DTO 定义请求、响应、分页契约。
- 模型 只做 ORM 映射，不承载业务流程。
- 新增安全分支、权限拒绝分支、配额拒绝分支必须补 service 单测。

## 5. 前端开发标准

前端新增应用默认按应用目录落位：

```text
frontend/src/apps/{app_code}/
  manifest.ts
  routes.ts
  api.ts
  views/
  components/
  composables/
  types/
```

历史兼容模块可继续按现有结构维护：

```text
frontend/src/api/{module}.ts
frontend/src/views/{Module}View.vue
frontend/src/types/{module}.ts
```

要求：

- 历史全局模块 API 调用集中在 `frontend/src/api`；新应用私有 API 放在 `frontend/src/apps/{app_code}/api.ts`。
- 跨应用复用的 API 只能通过稳定 public wrapper 暴露，不得直接 import 其他应用私有 API 文件。
- 页面使用 Vue 3 Composition API 与 `<script setup>`。
- 列表页面优先使用统一列表组件 `NeuroAgentListPage`。
- 菜单和按钮显示以后端权限、套餐功能、租户菜单覆盖为准。
- 不得在组件中硬编码角色判断。
- 表单必须有前端校验，后端错误必须转为用户可理解提示。
- 页面必须处理 loading、empty、error 三态。
- 列表、表格和抽屉不得产生无意义内滚动条；页面级滚动、表格横向滚动和弹窗内部滚动必须边界清晰。
- 分页必须以后端 `total` 为准；当当前页无数据且存在上一页时，前端应自动回退到有效页；无数据时不得展示虚假的多页分页。
- 操作列按钮必须稳定不换行，Chrome、Safari 等主流浏览器均需验证。
- 搜索区与操作区应左右分区，搜索条件一行优先，重置按钮只在存在输入或选择条件时出现。

## 6. 数据库设计标准

业务数据表设计必须遵守：

- 租户业务表必须有 `tenant_id`。
- 涉及组织上下文的业务表应有 `company_id`、`department_id` 或明确说明例外。
- 主数据默认必须有 `deleted_at`。
- 编码、手机号、业务编号等唯一字段必须考虑逻辑删除后的唯一键释放。
- 状态字段必须有明确枚举含义。
- 创建时间、更新时间、创建人、更新人按业务需要补充；当前底座未统一强制所有表都有操作人字段，新增模块如需要审计追溯应补齐。
- 不得为了方便使用物理删除清理业务主数据。

数据库结构变更必须同步：

- ORM 模型
- 生产 SQL 初始化或迁移脚本
- SQL / 数据库设计文档
- 回滚或验证说明

初始化和 seed 必须只做缺失补齐与必要纠偏：

- 不得覆盖租户已经修改的菜单名称、图标、排序、启停和覆盖配置。
- 不得覆盖平台人工移出套餐中心的功能点。
- 不得覆盖套餐列功能开关、配额值、租户订阅、租户覆盖和角色授权。
- 重启服务、重复执行 seed 或重复装载 Manifest 后，核心资源数量必须稳定。
- 必须修复数据源或同步脚本，禁止依赖前端隐藏来掩盖 seed 覆盖问题。

## 7. 菜单权限接入标准

新增菜单、按钮或操作时，必须明确：

| 项 | 说明 |
|---|---|
| 菜单 path | 前后端稳定一致 |
| 操作码 | 如 `xxx:create`、`xxx:edit`、`xxx:delete` |
| 权限类型 | 菜单、按钮、操作、数据权限 |
| 应用归属 | 必须能追溯到 `app_code` |
| 是否平台专属 | 平台专属不得进入租户套餐功能池 |
| 是否套餐功能 | 是否同步到 `saas_feature` |
| 租户是否可见 | 普通租户是否能看到 |
| 租户是否可覆盖 | 是否允许改名称、图标、启停 |
| 数据权限模式 | `ALL`、`SELF`、`ORG`、`ORG_SUB`、`CUSTOM` 等当前实现支持的模式 |

后端接口必须使用统一权限依赖，例如菜单路径、操作码、套餐功能、配额校验入口。前端权限隐藏不能替代后端校验。

权限归属必须按以下语义处理：

| 归属 | 语义 | 是否进入套餐 | 租户侧处理 |
|---|---|---|---|
| 系统内置 | 底座固定能力或不可售卖的内部能力 | 否 | 可展示为内置，不允许租户购买或移出 |
| 仅平台 | 只有平台管理员可见可操作 | 否 | 不进入租户菜单，不进入套餐 |
| 租户菜单 | 租户可购买、可开通、可授权的菜单或操作 | 是 | 进入套餐、租户菜单、角色权限 |
| 仅主体 | 租户只能管理自己主体的配置或品牌等能力 | 否 | 可由租户使用，但不作为可购买套餐功能 |

归属变更必须同步处理：

- 从“租户菜单”改为“仅平台 / 仅主体 / 系统内置”时，必须从套餐中心移出并记录原因。
- 从“仅平台 / 仅主体 / 系统内置”改为“租户菜单”时，必须明确是否加入套餐中心；未加入时不得出现在租户开通套餐详情。
- 平台菜单管理中的“加入套餐中心 / 移出套餐中心”是平台侧治理操作，必须纳入权限体系，但自身不得进入套餐。

## 8. 套餐与配额接入标准

新增业务能力必须判断是否进入套餐。

如果进入套餐，必须明确：

- 功能编码。
- 功能类型：目录、菜单、操作、能力、服务、配置。页面展示必须使用中文语义，不得直接暴露内部枚举。
- 是否由菜单/操作权限自动同步为功能点。
- 属于哪些默认套餐。
- 是否有配额。
- 配额编码。
- 配额类型：静态资源上限或动态周期消耗。
- 配额单位。
- 功能关闭后，对应配额是否隐藏或禁止保存覆盖值。

运行时必须遵守：

```text
租户订阅有效
  -> 套餐启用
  -> 套餐功能允许
  -> 租户功能覆盖
  -> 角色权限允许
  -> 数据权限允许
  -> 配额未超限
```

配额来源优先级：

```text
tenant_quota_override > saas_plan_quota
```

不得再把 `tenant.max_users`、`tenant.max_companies`、`tenant.expire_date` 作为业务判断来源。

套餐能力树必须遵守：

- 菜单管理生成的功能点必须按应用分组，再按目录、菜单、操作三层展示。
- 上层状态由下层计算；菜单开启不代表所有操作自动开启。
- 菜单下任一操作开启时，菜单显示“部分”或“已开”；全部操作开启时，菜单显示“已开”；全部关闭时显示“未开”。
- 目录和业务域用于分组和批量操作，不能替代下层菜单/操作真实状态。
- 保存套餐列时只能保存当前列的功能与配额配置，不得把未开、部分的能力误批量开启。
- 已停用或逻辑删除的套餐不得给新租户选择；已购买租户保留历史订阅效果。

## 9. 数据权限接入标准

新增业务列表、详情、导出、统计接口时，必须明确数据范围：

- 平台管理员是否可跨租户。
- 租户管理员是否可看全租户。
- 普通用户按组织、本人、业务单元还是自定义范围过滤。
- 是否需要组织和业务单元组合过滤。
- 是否需要导出与列表保持同样数据范围。

数据权限必须在 SQL 或 ORM 查询层生效，禁止先查询全量数据后再在应用层或前端过滤。

## 10. 字典与参数使用标准

业务中出现可配置枚举、类型、开关、阈值时，优先判断是否进入字典或参数体系。

适合字典：

- 类型
- 状态
- 分类
- 业务来源
- 可展示选项

适合参数：

- 默认值
- 系统开关
- 阈值
- 策略配置
- 页面或流程控制参数

当前底座采用“平台默认定义 + 租户覆盖”模式：

- 平台维护默认定义。
- 租户只保存覆盖值。
- `tenant_editable=false` 或 `is_platform_only=true` 的配置不可由普通租户覆盖。

字典和参数必须遵守：

- 平台专属字典只服务平台治理，不下发给普通租户页面。
- 非平台专属且允许租户使用的字典项，租户侧必须可读取默认项与覆盖项。
- 配额单位优先走数据字典，静态配额默认无周期，动态配额才需要周期单位。
- 菜单管理、套餐中心、组织架构、岗位、用户创建等页面不得硬编码字典值；确需兜底时必须标注并补初始化数据。

## 11. 日志审计标准

新增业务写操作必须考虑审计日志：

- 新增
- 编辑
- 逻辑删除/归档/停用
- 状态变更
- 权限变更
- 套餐或配额变更
- 导入导出
- 文件上传下载删除
- 关键配置变更

审计日志不得记录密码、token、密钥、敏感连接串或一次性明文凭据。

## 12. 文件与导入导出标准

涉及文件能力时必须遵守：

- 文件访问必须限制在当前 tenant 目录内。
- 下载、删除必须先校验安全 id 和 tenant 权限。
- 删除业务文件默认进入租户回收或归档策略，不得直接破坏审计追溯。
- CSV/Excel 导入必须限制大小、处理编码、校验字段。
- CSV/Excel 导出必须防公式注入。
- 导入导出必须接入套餐功能和配额校验。
- 导出数据范围必须与当前用户数据权限一致。

## 13. 接口设计标准

接口必须遵守当前统一契约：

- 返回 `code`、`message`、`data`。
- 成功 `code=0`、`message=ok`。
- 列表返回 `items`、`total`，分页参数使用 `skip`、`limit`。
- 不返回裸数组。
- 创建返回完整对象。
- 更新返回最新对象。
- 删除返回可预测结果。
- 业务错误码必须统一，不得散落魔法数字。

接口变更必须同步：

- 后端 DTO
- 前端 API 类型
- 页面调用
- 权限配置
- 必要文档

## 14. 测试验收标准

新增业务模块至少关注：

| 测试点 | 验收说明 |
|---|---|
| tenant 隔离 | 不同租户不能互相读写 |
| 权限拒绝 | 无菜单/操作权限时接口拒绝 |
| 套餐拒绝 | 套餐未开通功能时接口拒绝 |
| 配额拒绝 | 超出资源或周期额度时接口拒绝 |
| 数据权限 | 普通用户只能看到授权范围内数据 |
| 逻辑删除 | 删除后列表不可见，历史可追溯 |
| 唯一键释放 | 逻辑删除后可重新创建同编码业务对象 |
| 审计日志 | 关键写操作有日志 |
| 应用链路 | app_code、Manifest、菜单、权限、套餐、租户菜单、角色权限一致 |
| seed 幂等 | 服务重启或 seed 重跑不得覆盖人工移出套餐、租户覆盖和角色授权 |
| 前端体验 | 无重复滚动条、无越界、无按钮换行、刷新后菜单高亮正确 |
| 前端构建 | `npm run build` 通过 |

详细测试用例入口见 `docs/test_cases/`。新业务模块上线前除验证自身业务逻辑外，还必须通过 `docs/test_cases/99-业务功能接入回归测试用例.md` 中的底座接入准入项。

文档或标准变更至少执行：

```bash
git diff --check
```

## 15. 文档沉淀标准

新增业务模块完成后，应按影响范围更新：

- 需求设计：`docs/req_design/`
- 技术设计：`docs/tech_design/`
- 数据库设计：`docs/sql_design/`
